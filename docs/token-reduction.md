# LLM 処理トークン削減 — 実施内容と結果

対象: `src/Code.gs`（問い合わせメール → Gemini 要約 → Notion 登録）
方針: **要約・締切日抽出の品質（処理能力）を落とさずに**、LLM へ送受信するトークン量を削減する。

> 補足: 本リポジトリの他ブランチ（`claude/email-notion-automation-91q5bj`）を確認したが、
> トークン削減の実装は存在しなかった（両ブランチとも同一コミット）。
> 引用除去・署名除去などは一般に知られた手法だが、本実装はそれらを参考に
> このコードベース向けにゼロから書き起こしたもので、他実装のコード流用はない。

---

## 1. 実施した施策

### 施策① 本文圧縮 `compressBody()`（新規・効果最大）

LLM へ送る前に、**要約品質に寄与しない定型部分だけ**を本文から除去する。
問い合わせ内容そのものには一切手を加えない。

| 除去対象 | 理由 |
| --- | --- |
| 返信引用ヘッダ以降（`On ... wrote:` / `-----Original Message-----` / Gmail 日本語形式 `2026年7月8日(水) ... <addr>:`） | 過去のやり取りは要約対象外。処理対象は常に最新メッセージ |
| `>` で始まる引用行 | 同上 |
| 署名区切り `-- ` 以降 | 送信者情報は `送信者` プロパティで別途保存済み |
| URL → `[URL]` に置換 | トラッキングパラメータ付き URL は 1 本で数十トークンを浪費し、要約に不要 |
| 装飾罫線行（`━━━━` / `====` / `＊＊＊＊` 等） | 視覚装飾のみ |
| 連続する同一行・過剰な空白 | 定型フッターの繰り返し対策 |

**品質フォールバック**: 圧縮後の本文が最小長（10 文字）を下回った場合
（本文が引用のみのメール等）は、**原文にフォールバックして従来どおり処理**する。
圧縮が原因で処理不能・情報欠落になるケースを構造的に排除している。

### 施策② 切り詰めロジックの改善（トークン削減 + 品質向上）

- 旧: 先頭 4,000 字のみ残す + 長い省略注記（`【本文が長すぎるため、省略されています】` ≈ 20 トークン）
- 新: **先頭 75% + 末尾 25%** を残す + 短い注記（`…(中略)…` ≈ 7 トークン）

ビジネスメールでは締切・連絡先が末尾に書かれることが多く、
先頭切りでは長文メールの締切情報が失われ得た。新方式では末尾も保持されるため、
**トークン削減と同時に締切日抽出の再現率が向上**する（品質はむしろ改善）。

### 施策③ プロンプト指示文の短縮

意味・制約（構造化出力 `要約:` / `締切日:` の強制）を変えずに指示文を圧縮。

```
旧 (約60トークン)                          新 (約35トークン)
以下のメール本文を日本語で要約してください。      次のメール本文を日本語で要約し、この形式のみで出力:
次の形式で厳密に出力してください（余計な説明は不要）: 要約: <3行程度>
要約: <3行程度の要約>                        締切日: <YYYY-MM-DD、無ければ「なし」>
締切日: <YYYY-MM-DD 形式。締切が無ければ「なし」>
メール本文:                                本文:
```

毎回の呼び出しで約 25 トークンを固定削減。パーサ（`parseGeminiResult`）が要求する
出力形式は完全に同一のため、後段処理への影響はない。

### 施策④ `generationConfig` の追加（出力側のガード）

```js
generationConfig: {
  temperature: 0.1,      // 形式遵守を安定させ、再試行(=トークン浪費)を減らす
  maxOutputTokens: 256   // 要約3行+締切日で十分な上限。暴走出力を防止
}
```

- 通常の応答（3 行要約 + 締切日 ≈ 100〜150 トークン）には影響しない**上限ガード**。
  モデルが冗長な説明を付け始めた場合の出力トークン浪費を確実に止める。
- 低 temperature により構造化出力の形式ブレが減り、パース失敗 → 再処理という
  間接的なトークン浪費も抑制される。

## 2. 削減結果（実測）

計測スクリプト: [`scripts/measure-tokens.js`](../scripts/measure-tokens.js)（`node scripts/measure-tokens.js` で再現可能）

- 旧パイプライン: 圧縮なし・先頭切り詰め・旧プロンプト（変更前の実装を再現）
- 新パイプライン: `compressBody` + 先頭/末尾切り詰め + 短縮プロンプト（実装をそのまま使用）
- トークン推定: CJK 文字 ≈ 1 tok/字、その他 ≈ 1 tok/4 字（日本語ビジネス文での実測に近い保守的近似）

| サンプル | 元本文(字) | 旧プロンプト(推定tok) | 新プロンプト(推定tok) | 削減(tok) | 削減率 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1. 標準的な問い合わせ（署名付き） | 436 | 322 | 192 | 130 | **40.4%** |
| 2. 返信チェーン付き（引用2通分） | 752 | 527 | 160 | 367 | **69.6%** |
| 3. URL・装飾の多い案内系問い合わせ | 836 | 494 | 216 | 278 | **56.3%** |
| 4. 超長文（4000字超・引用チェーン含む） | 4,599 | 3,805 | 3,699 | 106 | 2.8% |
| 5. 短い問い合わせ（圧縮対象が少ないケース） | 51 | 134 | 99 | 35 | 26.1% |
| **合計** | - | **5,282** | **4,366** | **916** | **17.3%** |

### 読み方

- **最も多い実運用パターン（返信チェーン・署名付き = サンプル1〜3）で 40〜70% 削減。**
  問い合わせメールは返信でやり取りが続くほど引用が積み上がるため、実運用の平均削減率は
  合計値 17.3% より上振れしやすい（サンプル4のような 4,000 字級の単発長文は稀）。
- サンプル4（超長文）は圧縮後も本文が上限近くまで残るため削減率は小さいが、
  切り詰め方式の改善により**末尾の締切・連絡先が残るようになり品質は向上**している。
- サンプル5（短文）はもともと無駄が少なく、削減は主にプロンプト短縮分（約35tok）。
- 上記は入力側のみの実測。出力側は `maxOutputTokens: 256` により冗長出力時の
  浪費が確実に頭打ちになる（通常時は無影響）。

## 3. 品質（処理能力）を落とさないための担保

| 担保 | 内容 |
| --- | --- |
| 除去対象の限定 | 削るのは引用・署名・URL・装飾のみ。問い合わせ本文の文言は不変（`compressBody: 本文そのものは変更しない` テストで保証） |
| 原文フォールバック | 圧縮で本文が最小長を割る場合は原文で処理（引用のみのメールも従来どおり登録される） |
| 出力形式は不変 | プロンプト短縮後も `要約:` / `締切日:` の構造化出力を強制。パーサ・Notion 登録処理は無変更 |
| 切り詰め品質の向上 | 先頭+末尾保持により、旧仕様で失われ得た末尾の締切情報が保持される |
| 上限は余裕を確保 | `maxOutputTokens: 256` は通常出力(≈100〜150tok)の約2倍 |
| 回帰テスト | 既存 40 件のテストを全て維持しつつ 9 件追加（計 49 件、全パス）。引用・署名が Gemini に送られないこと、フォールバック動作、`generationConfig` 送信を統合テストで検証 |

```
# tests 49
# pass 49
# fail 0
```

  現行のラベル形式パースで十分機能しているため今回は見送り。
